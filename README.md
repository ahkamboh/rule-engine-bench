# rule-engine-bench

Five implementations of the same prop firm rule evaluation, run over the same
synthetic data, checked against each other for identical verdicts, and measured.

The question it answers: when a rule evaluation service stops keeping up, is the
language the problem? On this workload it is worth about 2x. The data format is
worth about 80x.

## Why this exists

I built a rule evaluation pipeline in production. That code, its data, and its
numbers belong to my employer and I cannot publish any of it. So this is the same
problem rebuilt from nothing in September 2026: my own rule set, my own generated
accounts, my own measurements, on a laptop anyone can compare against.

Nothing here came from a production system. The account data is generated by
`src/generate.ts` from a seeded PRNG, so `--seed=42` gives you the same 100,000
accounts it gave me.

## The rules

Five rules, applied per account over its trades in time order. Defaults live in
one place per engine (`src/rules.ts` and `rust/src/main.rs`) and match:

| rule | default | meaning |
|---|---|---|
| max daily loss | 5% | equity dropping more than this below the day's opening equity fails the account |
| max total drawdown | 10% | equity falling more than this below peak equity fails the account |
| profit target | 10% | above initial balance, and no rule breached, passes the account |
| minimum trading days | 4 | days with at least one trade |
| consistency | 0.5 | the best single day cannot be more than half of total profit |

A breach ends the walk immediately, which is why the engines read 3,955,749 of
the 7,184,820 stored trades. Every rate below uses the trades actually read.

On the default dataset: 51,391 accounts fail on daily loss, 12,990 fail on
drawdown, 4,768 pass, and 30,851 are still in progress at the end of their
history. The 4.8% pass rate was not tuned for, it fell out of the generator.

## The data

A flat binary file, little endian, fixed width records, no framing. The header is
32 bytes, an account is 16, a trade is 16, and every record sits on an 8 byte
boundary so both engines read fields without copying. The layout is written out
at the top of `src/format.ts`.

Trades are stored in ascending time order per account, so no engine sorts.
Account records vary in length, so both engines build an offset index in one scan
before any work can be split across threads.

`src/to-jsonl.ts` writes the same accounts out as JSON, one object per line, for
the idiomatic engine to read. Same accounts, same trades, same order. 111 MB as
binary, 462 MB as JSON.

## Results

Apple M1 Pro, 10 cores, 32 GB, node v26.8.1, rustc 1.96.0, median of 21 passes.
Cost assumes $0.036 per vCPU-hour, roughly an on demand ARM core.

| engine | threads | wall | accounts/sec | CPU s per 1M | $ per 1B | peak RSS |
|---|---|---|---|---|---|---|
| node, JSON in, objects per trade | 1 | 1647.7 ms | 60,692 | 16.477 | $0.1648 | 243 MB |
| node, binary buffer, no allocation | 1 | 20.6 ms | 4,865,923 | 0.206 | $0.0021 | 297 MB |
| node, binary buffer, worker_threads | 10 | 3.0 ms | 33,231,788 | 0.301 | $0.0030 | 559 MB |
| rust, single thread | 1 | 10.1 ms | 9,931,678 | 0.101 | $0.0010 | 113 MB |
| rust, rayon | 10 | 1.6 ms | 63,658,789 | 0.157 | $0.0016 | 113 MB |

Latency, sampled on the last warm pass:

| engine | unit | p50 | p99 |
|---|---|---|---|
| node, JSON in | 1 account | 15.0 us | 26.1 us |
| node, binary buffer | 1000 accounts | 220.8 us | 349.4 us |
| rust, single thread | 1000 accounts | 101.3 us | 126.7 us |

All five produce checksum `33984963` and read exactly 3,955,749 trades.
`results/results.json` is this run, with per pass timings and the machine it ran
on. Wall times move a few percent between runs, and the parallel rows move most
because they are only a few milliseconds long.

## What the numbers say

The format did the work. Going from a JSON object per account to a binary buffer
with no allocation per trade took one thread from 60,692 to 4,865,923 accounts
per second, which is 80x, and it never left JavaScript. Of the 1648 ms the
idiomatic engine spends, 1502 ms is `JSON.parse`, so 91% of its time goes on
turning bytes into objects it then throws away. Its rule evaluation is 26.2 ms,
about the same as the tuned engine's entire runtime. The rule math was never the
bottleneck, and rewriting only the rule math in a faster language would have
bought almost nothing.

Rust is worth about 2x on the same algorithm, 9.9M against 4.9M accounts per
second on one thread. Real, and much smaller than the format change.

Where Rust separates is tails and memory. Same walk, but p99 per thousand
accounts is 126.7 us against 349.4 us, and peak RSS is 113 MB against 297 MB for
a 111 MB file. Node's pool reaches 559 MB because every worker gets its own heap
even though all ten address one `SharedArrayBuffer`. On a box sized by memory
rather than by CPU, that ratio decides how many tenants fit.

Both scale about the same across ten cores, 6.8x for node's pool and 6.4x for
rayon, and both lose the rest to memory bandwidth. Node's pool costs 34 ms to
spawn and its first pass runs 21x slower than its steady state while each
worker's JIT warms up, so a process that starts, does one batch and exits never
sees 33M. Rust's first pass is within 10% of its median, single threaded or
parallel.

Parallel work is faster in wall time and more expensive in CPU time. Rayon does
1.6 ms of wall for 0.157 CPU seconds per million, against 0.101 for one thread.
If you are paying for cores and not for latency, one thread per request is the
cheaper answer.

## Measurement notes

Two bugs in my own benchmark, both of which would have produced a publishable
looking lie.

The first version of the Rust reader pulled bytes out one at a time,
`u32::from_le_bytes([data[at], data[at+1], ...])`, which costs a bounds check per
byte. Rust measured 21.9 ms against node's 20.8 and I nearly wrote up "the
language does not matter". Reading through `data[at..at+8].try_into()` instead is
one bounds check and one unaligned load, and the same code took 10.1 ms. The
language mattered twice as much as my first measurement said.

The tail latencies were originally sampled on the first pass, where node's p99
came out at 1777 us against Rust's 297. That gap was almost entirely V8 tiering
up. Sampled warm, on the last pass, node's p99 is 349 us. Real difference, 5x
smaller than the number I would have published.

Node got the same scrutiny as Rust. Every record in the file is 8 byte aligned,
so the buffer can be read through `Float64Array` and `Uint32Array` and skip a
method call per field, which is the usual advice. It came out 6% slower than
`DataView` (22.4 ms against 21.0), so `DataView` is the default and
`--reader=typed` is kept in `src/rules.ts` to show the result.

Timing rules: median of 21 passes over a warm in memory buffer, so the disk is
out of the picture except for the idiomatic engine where reading the file is part
of its cost. The scanned trade counter is derived from the cursor after the loop
instead of incremented inside it, so counting costs nothing per trade. Peak RSS
comes from `/usr/bin/time -l` on the whole process rather than from each runner's
own reading, which would miss allocator overhead and the worker heaps.

## Checking that the engines agree

A faster engine that disagrees is not a faster engine. Each one adds an FNV-1a
hash of `(id, verdict, final equity in cents)` per account and reports the sum.
Addition means the total does not depend on thread scheduling, and the sum is
sensitive to any change in verdict or final equity. Both engines also report how
many trades they read before deciding, which catches a rule that fires one trade
early or late while still reaching the same verdict.

`npm run verify` fails with a non-zero exit if any engine disagrees on either.

## Reproduce

Needs node 23 or newer, for running TypeScript without a build step, and a Rust
toolchain.

```sh
npm run gen                      # writes data/accounts.bin, 111 MB, about 4 s
npm run jsonl                    # writes data/accounts.jsonl, 462 MB
cargo build --release --manifest-path rust/Cargo.toml
npm run bench                    # runs all five, writes results/
```

`npm run verify` is the same thing with one pass, for a quick check that the
engines still agree. Its timings are cold and should not be quoted: on one pass
the worker pool spends more time warming up than working, and it reports about
1.7M accounts per second against the 30M it settles at.

Individual engines, if you want to change one thing at a time:

```sh
node src/run-idiomatic.ts --passes=3
node src/run-single.ts --passes=21 --reader=dataview
node src/run-workers.ts --passes=21 --threads=10 --chunk=2000
./rust/target/release/rule-engine-bench --mode=single --passes=21
./rust/target/release/rule-engine-bench --mode=rayon --passes=21 --chunk=2000
```

A bigger or smaller workload:

```sh
node src/generate.ts --accounts=500000 --avg-trades=120 --seed=7
```

Each engine prints one line of JSON. `npm run bench` collects those into
`results/results.json` with the machine it ran on, and `results/results.md`.

## What this does not prove

It is one workload on one machine. The accounts are generated, not real, and
generated data has a shape: my trades are normal with a small negative edge, so
there are no gaps, no weekends, no correlated blowups, and no adversarial
histories.

The rule set is mine and it is a plausible version of a common one, not any
particular firm's. Real rule sets carry more conditions and more exceptions, and
the exceptions are usually what makes them slow.

Everything here is CPU over an in memory buffer. It says nothing about the queue
in front of it, the database behind it, or what happens when the rules change
while accounts are mid evaluation, which in production is the harder half.

The comparison is between engines I wrote. Somebody who writes Rust or V8 for a
living would find more in both. The measurement notes above are two examples I
caught in an afternoon.
